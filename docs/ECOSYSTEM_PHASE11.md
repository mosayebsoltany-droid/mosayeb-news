# فاز ۱۱ — سرویس جانبی، صف پایدار و داشبورد مدیر — نسخه ۰٫۸٫۰

همهٔ استعلام‌ها و اعلان‌ها شبیه‌سازی‌اند. این نسخه هیچ پیامک واقعی نمی‌فرستد و به دولت، ثبت احوال، شاهکار، امضای دیجیتال، بانک یا سامانهٔ قضایی وصل نیست. توسعهٔ صف و UI با حفظ احراز هویت، کنترل نرخ و داده‌های موجود انجام شده است.

## داشبورد گرافیکی

صفحهٔ `/admin` فرم ورود فارسی، چهار کارت آمار ۳۰ روزه، نام فعال‌ترین broker، نمودار ستونی موفق/ناموفق هفت روزه و جدول قابل دسترس دارد. پوستهٔ صفحه عمومی است؛ داده‌های `/analytics/dashboard` و `/admin/analytics/chart-data` فقط با JWT حساب admin فعال دریافت می‌شوند. بدون توکن ۴۰۱ و برای broker برابر ۴۰۳ است. توکن در حافظهٔ همان صفحه است و با خروج پاک می‌شود؛ کوکی یا localStorage برای آن ساخته نمی‌شود. رمز در log یا HTML خروجی ذخیره نمی‌شود.

در حساب دارای دسترسی سرور، مدیر را مطابق راهنمای فاز ۱۰ با `python -m app.create_user نام_مدیر --role admin` بسازید. حساب مدیر یا رمز پیش‌فرض اضافه نشده است. از رمز اصلی GitHub برای ورود به این صفحه استفاده نکنید؛ این حساب متعلق به خود برنامه است.

خروجی `GET /admin/analytics/chart-data` شامل `labels` و `datasets` سازگار با Chart.js است. روزهای بدون پرونده صفر پر می‌شوند و یک query گروه‌بندی‌شده، هر هفت روز را محاسبه می‌کند. بازه، UTC شامل امروز و شش روز قبل است. نمودار UI با SVG محلی رسم می‌شود و به CDN یا سرویس ثالث نیاز ندارد. دادهٔ واقعی پرونده‌ها مبناست؛ دادهٔ ساختگی ثابت به‌عنوان آمار واقعی نمایش داده نمی‌شود.

## سرویس‌های جانبی Mock

| مسیر | دسترسی | رفتار |
| --- | --- | --- |
| POST /external/verify-national-id | کاربر فعال | دقیقاً ۱۰ رقم ASCII؛ پیشوند ۰۰ قاعدهٔ اعتبار ساختگی است؛ simulation=true |
| POST /external/send-sms | admin فعال | پیش‌نمایش درگاه؛ status=simulated و رسید SIM-SMS؛ هیچ ارسال واقعی ندارد |
| GET /notifications/{event_id} | فقط مالک رویداد | وضعیت pending/processing/completed/failed، attempts و رسید آزمایشی |

شناسهٔ ملی واقعی وارد نکنید. endpoint پیشوند ۰۰ مستقل از Mock حیات/وفات فاز ۱۰ است؛ قواعد ساختگی آن مرحله و رفتار ثبت ادعا عوض نشده‌اند. endpoint پیامک، قالب شمارهٔ `09` به‌همراه ۹ رقم یا شناسهٔ ساختگی `DEMO-USER-<id>` و متن حداکثر ۵۰۰ کاراکتر را می‌پذیرد. شماره و متن درگاه چاپ یا ذخیره نمی‌شوند و رسید برای یک event_id ثابت است. درخواست مستقیم پیش‌نمایش پیامک وارد صف پرونده‌ها نمی‌شود.

## صف و worker

پس از موفقیت ثبت ادعای احرازشده، یک `NotificationEvent` در همان تراکنش تغییر وضعیت موفق پرونده و AuditLog ثبت می‌شود. یکتایی document_request_id از چند رویداد برای همان پرونده جلوگیری می‌کند. پاسخ HTTP منتظر ارسال اعلان نمی‌ماند و هدر `X-Simulated-Notification-ID` شناسهٔ رویداد را می‌دهد. ادعای ناموفق یا رد هویت، رویداد اعلان ندارد.

worker از صف SQL پایدار می‌خواند و درگاه Mock داخل فرایند را با HTTPX/ASGI صدا می‌زند. گیرنده `DEMO-USER-<id>` است؛ هیچ شمارهٔ واقعی برای کاربر حدس زده نمی‌شود. متن اعلان شامل کد رهگیری همان پرونده است و رسید `SIM-SMS-<event_id>` برمی‌گردد.

- وضعیت pending فقط پس از زمان available_at قابل برداشت است.
- برداشت با UPDATE شرطی انجام می‌شود؛ lease سی‌ثانیه‌ای و token یکتا مانع پذیرش نتیجهٔ worker قدیمی پس از واگذاری مجدد می‌شوند.
- حداکثر سه تلاش؛ پس از خطا، backoff افزایشی و سپس failed پایدار.
- timeout درگاه پنج ثانیه است. پاسخ خراب یا ناسازگار، موفق تلقی نمی‌شود.
- worker کشته‌شده رویداد را حذف نمی‌کند؛ پس از پایان lease امکان بازیابی هست. انقضای lease آخرین تلاش، failed می‌شود.
- تکمیل/شکست نهایی با SIM_NOTIFICATION_DONE/FAILED در AuditLog ثبت می‌شود؛ متن و شماره در audit نیستند.

این طراحی صف SQL/outbox است، نه Celery. وابستگی بلااستفادهٔ Celery نصب نشده است. Redis فاز ۱۰ برای کنترل نرخ باقی است. برای پیامک واقعی، آداپتور و قرارداد ارائه‌دهنده، رضایت/گیرندهٔ واقعی و idempotency ارائه‌دهنده لازم‌اند. retry ماهیت at-least-once دارد؛ تضمین exactly-once در سرویس خارجی ادعا نمی‌شود.

## اجرا و استقرار

در SQLite، worker پیش‌فرض همراه lifespan برنامه اجرا و هنگام shutdown مدیریت‌شده لغو می‌شود. جدول جدید با create_all فقط به‌صورت افزایشی ساخته می‌شود. رویدادها داخل همان فایل پایگاه داده می‌مانند.

```bash
docker compose up --build --detach --wait
```

در PostgreSQL، سرویس `migrate` ابتدا Alembic را تا 0002 اجرا می‌کند؛ سرویس `worker` جداگانه با همان تصویر و محیط دیتابیس شروع می‌شود. worker در API خاموش است تا پردازش جدا و روشن باشد. دادهٔ volume قبلی حفظ می‌شود.

```bash
BROKER_RATE_LIMIT_STORAGE_URI=redis://redis:6379/0 docker compose -f compose.postgres.yaml --profile cache up --build --detach --wait
```

worker جدا با `python -m app.worker` نیز قابل اجراست؛ schema باید از قبل آماده باشد. `BROKER_NOTIFICATION_WORKER_ENABLED=false` پردازش همراه API را خاموش می‌کند. `BROKER_NOTIFICATION_POLL_SECONDS` پیش‌فرض یک ثانیه و بازهٔ مجاز ۰٫۱ تا ۱۰ ثانیه است. هنگام خاموش بودن همهٔ workerها، صف حفظ می‌شود ولی پردازش نمی‌شود. worker Compose فعلاً healthcheck heartbeat ندارد؛ `/ready` فقط دیتابیس و storage کنترل نرخ API را بررسی می‌کند و تضمین زنده‌بودن worker نیست.

در پایگاه PostgreSQL موجود، backup معتبر داشته باشید و پیش از API جدید، migration را اجرا کنید. 0002 فقط جدول صف، روابط و ایندکس‌ها را اضافه می‌کند. downgrade این migration صف را حذف می‌کند و روی دادهٔ واقعی در این فاز اجرا نشده است. انتقال داده از SQLite به PostgreSQL همچنان انجام نشده است.

## آزمون و حدود تحویل

آزمون‌ها پوشش می‌دهند: دسترسی مدیر و مالک، قواعد Mock، پاسخ بدون انتظار درگاه، transaction rollback، یکتایی رویداد، تکمیل با رسید و audit، backoff و سقف تلاش، بازیابی lease و رد نتیجهٔ worker قدیمی، شکست پس از crash آخرین تلاش، shutdown lifespan، نمودار هفت‌روزه و حفظ اطلاعات migration قبلی. در CI، PostgreSQL واقعی و worker جدا، تکمیل اعلان پس از ثبت ادعا را بررسی می‌کنند.

صف SQL برای این شبیه‌سازی ساده و قابل بررسی است؛ سنجش ظرفیت، backlog alert، پاک‌سازی/آرشیو رویدادها، مانیتورینگ heartbeat و آزمون بار چندworker هنوز انجام نشده‌اند. اتصال رسمی، پیامک واقعی و امضای دیجیتال پیاده نشده‌اند.
