# فاز ۱۲ — سخت‌سازی و آزمون امنیتی محدود، نسخه ۰٫۹٫۰

این گزارش وضعیت کد و آزمون‌های کنترل‌شده را توضیح می‌دهد؛ گواهی OWASP، تست نفوذ مستقل، انطباق بانکی یا تضمین «ضدگلوله» بودن نیست. هیچ حملهٔ حجمی یا آزمون مخرب روی سرویس عمومی/سامانهٔ دولتی انجام نمی‌شود. آزمون‌ها روی SQLite موقت و PostgreSQL/Redis یک‌بارمصرف CI هستند.

## کنترل ورود و نرخ

مسیر ورود همان `POST /auth/token` است. یک Limiter مشترک برای برنامه وجود دارد؛ نمونهٔ جدا برای هر روتر ساخته نشده است. سهمیهٔ ورود به پنج تلاش در دقیقه برای هر peer IP کاهش یافت؛ درخواست ششم ۴۲۹ و Retry-After می‌گیرد. سهمیهٔ ثبت ادعا پنج تلاش در دقیقه برای هر حساب باقی است. Redis مشترک برای چند پردازش و memory برای یک پردازش پشتیبانی می‌شوند. خطای storage به ۵۰۳ منجر می‌شود و کنترل نرخ غیرفعال نمی‌شود.

نام کاربری حداکثر ۱۰۰ و رمز حداکثر ۱۲۸ کاراکتر وارد بررسی می‌شوند؛ ورودی خارج از محدوده، پاسخ عمومی نامعتبر می‌گیرد. query نام کاربری پارامتری SQLAlchemy است. آزمون payload متنی SQL Injection روی دیتابیس تست، ورود را ممکن نمی‌کند. JWT فقط HS256 را می‌پذیرد؛ sub/exp/iat لازم‌اند، شناسهٔ کاربر باید عدد مثبت متعارف در محدودهٔ پشتیبانی‌شده باشد و دادهٔ خراب/منقضی‌شده ۴۰۱ می‌دهد. نقش داخل توکن مجوز مدیر نمی‌سازد؛ نقش و فعال بودن از دیتابیس خوانده می‌شوند.

این سهمیه‌ها فقط از مسیرهای مشخص محافظت می‌کنند؛ دفاع در برابر DDoS حجمی، WAF، ظرفیت‌سنجی، rate limiting لبه و سیاست ضدسوءاستفادهٔ توزیع‌شده هنوز جداگانه لازم‌اند. IP پشت NAT/پراکسی می‌تواند مشترک باشد. ۴۲۹ مسدودسازی موقت سهمیه است؛ سیستم کسی را بر اساس IP به‌عنوان «هکر» برچسب یا برای همیشه مسدود نمی‌کند.

## ممیزی امنیتی

AuditLog اکنون user_id اختیاری، ip_address و request_id دارد. شناسهٔ کاربرِ موجود در شکست رمز، و NULL برای حساب ناموجود ثبت می‌شود. اکشن شکست `FAILED_LOGIN_ATTEMPT` و اکشن موفق قبلی `LOGIN` است. متن شکست فقط `Credentials rejected` است؛ نام کاربری ورودی، رمز، توکن و body در آن نیستند. commit در اختیار مسیر فراخوان است تا ثبت پرونده، رویداد صف و audit هم‌تراکنش باقی بمانند.

IP از `request.client` و با اعتبارسنجی IPv4/IPv6 گرفته می‌شود؛ X-Forwarded-For مستقیم خوانده نمی‌شود. دستور Docker پیش‌فرض `--no-proxy-headers` دارد، پس پشت پراکسی معمولاً IP خود پراکسی ثبت می‌شود. نسبت دادن آن به فرد واقعی درست نیست. برای IP مبدأ واقعی، پراکسی باید هدر ورودی را پاک‌سازی و فقط IP/CIDR همان پراکسی در ASGI مورد اعتماد شود؛ همهٔ مبدأها را trusted نکنید.

`GET /admin/audit-logs?limit=50&offset=0` فقط برای admin فعال است (حداکثر limit=200 و offset=10000). شناسهٔ درخواست با X-Request-ID پاسخ قابل تطبیق است. IP فقط در دیتابیس ممیزی است، نه لاگ JSON عمومی access. دسترسی و دورهٔ نگه‌داری audit باید برای استقرار تعیین شوند.

پنج تلاش مجازِ ناموفق در دیتابیس ثبت می‌شوند. درخواست ردشده با ۴۲۹ وارد تابع login نمی‌شود و رکورد دیتابیس جدید نمی‌نویسد؛ وضعیت آن در access log دیده می‌شود. این کار از تبدیل سیل درخواست‌های ردشده به سیل INSERT ممیزی جلوگیری می‌کند.

## هدرها، CSP و HTTPS

- X-Frame-Options=DENY و frame-ancestors 'none' برای جلوگیری از iframe.
- X-Content-Type-Options=nosniff، Referrer-Policy=no-referrer و Cache-Control=no-store.
- Permissions-Policy دوربین، میکروفون، موقعیت و پرداخت مرورگر را غیرفعال می‌کند.
- صفحات `/admin` و `/portal` فقط اسکریپت/استایل nonceدار همان پاسخ را اجرا می‌کنند. nonce در هر پاسخ عوض می‌شود. دادهٔ گزارش با textContent/DOM ساخته می‌شود.
- Swagger نیز nonce دارد. فقط برای اسکریپت و CSS خود Swagger، CDN موجود jsDelivr مجاز است؛ استایل inline تولیدشدهٔ Swagger مجاز، ولی unsafe-inline برای script مجاز نیست. این دارایی CDN هنوز self-host نشده و ممیزی جاوااسکریپت آن در اسکن pip نیست.
- X-XSS-Protection=0 است؛ فیلتر قدیمی با مقدار ۱ در برخی مرورگرها خود می‌تواند مشکل ایجاد کند. CSP جایگزین اصلی این لایه است، نه جایگزین escaping و کنترل دسترسی.
- Strict-Transport-Security=max-age=31536000 فقط وقتی ASGI واقعاً scheme=https دارد فرستاده می‌شود. هدر جعلی X-Forwarded-Proto این تصمیم را تغییر نمی‌دهد. includeSubDomains و preload بدون کنترل و HTTPS همهٔ زیردامنه‌ها فعال نشده‌اند.

HTTP محلی برای توسعه/healthcheck باقی است. در محیط پشت پراکسی TLS مثل Codespaces، اگر ASGI HTTP ببیند، HSTS باید در لایهٔ TLS مورد اعتماد تنظیم شود؛ این کد گواهی TLS یا اجبار HTTPS در edge ایجاد نمی‌کند. تنظیم TLS و redirect ورودی HTTP مسئولیت استقرار است.

ورود برنامه کوکی نشست صادر نمی‌کند؛ JWT داشبورد در حافظهٔ صفحه است. بنابراین کوکی احراز هویت جدیدی برای تنظیم Secure/HttpOnly ایجاد نشده است. کوکی‌های GitHub/Codespaces متعلق به آن سرویس‌اند.

## سقف حجم پیش از parser

برای جلوگیری از پردازش فرم/فایل بسیار بزرگ قبل از رسیدن به handler، middleware بدنه را پیش از JSON/multipart/form محدود می‌کند؛ بدنهٔ chunked نیز محدود است. سقف ورود ۱۶ KiB، سایر POST/PUT/PATCHها ۶۴ KiB و مسیر نقشه ۶ MiB است. سقف فایل نقشه همچنان ۵ MiB است تا برای سربار multipart جا باشد. بدنهٔ بیش‌ازحد ۴۱۳ و طول نامعتبر/مبهم ۴۰۰ می‌گیرد. این یک سقف حافظه برای هر درخواست است؛ کنترل همزمانی و اندازه/زمان درخواست در reverse proxy همچنان لازم است.

## مهاجرت امن SQLite و PostgreSQL

مهاجرت 0003 دو ستون ممیزی را اضافه و user_id را nullable می‌کند. داده‌های ممیزی قبلی حفظ می‌شوند و ستون‌های جدید آن‌ها NULL هستند. در PostgreSQL سرویس migrate قبل از API جدید اجرا می‌شود.

SQLite قدیمی که با create_all ساخته شده و تاریخچهٔ Alembic ندارد، در startup با ساختار مرجع 0002 یا head مقایسه می‌شود (ستون، نوع، nullability، FK، index/unique، default و check constraint). فقط ساختار شناخته‌شده baseline می‌گیرد و upgrade می‌شود. ساختار ناشناخته یا دارای trigger/view متوقف می‌شود؛ برنامه آن را حذف یا بازنویسی نمی‌کند. نسخهٔ پشتیبان معتبر قبل از ارتقا لازم است. helper با `python -m app.migrate` نیز قابل اجراست. در حالت auto_create_tables=false مسئول استقرار باید migration را صریح اجرا کند.

Downgrade این تغییر عمداً متوقف می‌شود؛ بازگرداندن NOT NULL پس از ثبت رویداد بی‌کاربر نباید باعث حذف لاگ امنیتی شود. rollback نیازمند برنامه و backup بازبینی‌شده است. روی production هیچ downgrade یا حذف داده اجرا نشده است.

## شواهد و محدودیت ممیزی

تست‌ها شامل ورود پنجم/ششم، ثبت شکست با کاربر NULL و IPv4/IPv6، عدم اعتماد به هدر جعلی، دسترسی مدیر به audit، JWT خراب/منقضی/الگوریتم و نقش جعلی، payload SQL، CSP/nonce، HSTS روی HTTPS و عدم اثر X-Forwarded-Proto، بدنهٔ بیش‌ازحد/chunked و حفظ دادهٔ SQLite قدیمی هستند. سناریوهای PostgreSQL، Redis و worker قبلی هم اجرا می‌شوند.

CI یک job جدا برای `pip-audit` نیازمندی‌های runtime دارد؛ گزارش JSON به‌صورت artifact ذخیره می‌شود و انتشار تصویر به موفقیت تست و اسکن وابسته است. نتیجهٔ «بدون آسیب‌پذیری شناخته‌شده» فقط به دادهٔ همان اجرای اسکن و بسته‌های pip اشاره دارد؛ اسکن OS image، CDN/JS، کد سفارشی و امنیت زیرساخت را پوشش نمی‌دهد. تست نفوذ مستقل، بازبینی رمزنگاری/دسترسی سازمانی، آزمون بار و پوشش کامل OWASP Top 10 همچنان ادعا نمی‌شود.
